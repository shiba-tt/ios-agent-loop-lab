# 検証計画 — このリポジトリで何を検証し、今後の個人開発にどう活かすか

> 観点2への回答。副業として iOS アプリを量産・改善する前提での検証計画。

## このラボの最終成果物 = App Factory Kit

検証の目的は「このリポジトリで良いアプリを1本作る」ことではなく、**アプリ N 本に複製できる検証済みのループ一式**を手に入れること。

| 成果物 | 中身 | 検証元 |
|---|---|---|
| テンプレートリポジトリ | AppCore/AppShell 構成、XcodeGen 設定、CI、テンプレート類 | E01, E02, E06 |
| CLAUDE.md プレイブック | エージェント作業契約(何を自律でやり、何を聞くか) | E01, E05 |
| approval-policy | 変更クラスと承認ゲートの定義 | E03 |
| リリースパイプライン | fastlane + ASC API key + secrets 手順書 | E04 |
| メトリクス基盤 | loop-log.csv 運用と週次レビュー手順 | E05 |

## 検証したい問い(リサーチクエスチョン)

- **Q1 自律性**: コアロジック開発は、人間タッチ何回/PR まで減らせるか(目標: レビュー+マージの2回)
- **Q2 ゲート配置**: どこに承認ゲートを置けば「安全」と「速度」が両立するか。ゲートが形骸化(ラバースタンプ化)しないか
- **Q3 コスト**: アプリ1本を TestFlight に乗せるまでの人時と金額(CI 分数、API 利用料)はいくらか
- **Q4 自己改善**: L4(メタループ)を回すと、介入回数・CI 失敗率・サイクルタイムは実際に下がるか

## 実験一覧

| ID | 名前 | 仮説 | 主要メトリクス | 成功基準 |
|---|---|---|---|---|
| E01 | リモートコアループ | AppCore の機能開発はリモート Linux のみで、人間タッチ≤2回/PR で回る | human_touches, CI 初回 green 率 | 3 PR 連続でタッチ≤2、初回 green ≥2/3 |
| E02 | アプリ殻とシミュレータ CI | XcodeGen + macOS ランナーで UI 層の PR 検証が自動で回る | macOS CI 分数/PR、flake 率 | シミュレータテストが PR 毎に安定実行、flake<10% |
| E03 | HOTL ゲート運用 | 変更クラス制(C0〜C3)で、レビュー負荷を C1/C2 に集中できる | クラス別レビュー時間、差し戻し率 | C0 をノールック運用しても事故ゼロ、C2 差し戻しが検知される |
| E04 | TestFlight パイプライン | 内部配布まで完全自動、外部/Store は人間ゲートで安全に出せる | push→TestFlight 所要時間、署名起因の失敗数 | マージから内部配布まで人手ゼロ |
| E05 | 改善メタループ | 週次で spec/CLAUDE.md を更新すると介入回数が減る | 週別 human_touches 平均、同種失敗の再発数 | 4週で介入回数 30% 減、同種失敗の再発ゼロ |
| E06 | 2本目立ち上げ | テンプレートから新アプリを1日(人時ベース)で TestFlight 内部配布まで持ち込める | 人時/立ち上げ | 人時 ≤ 8h で TestFlight 内部配布 |

## 副業 KPI への接続

ループの良し悪しは最終的に次の KPI で判断する(L4 週次レビューで確認):

1. **人時/機能** — 1機能を出すのに人間が使った時間。エージェント代・CI 代より、副業では人時が最も高価
2. **人時/アプリ立ち上げ** — テンプレの質の指標(E06)
3. **月次ランニングコスト** — CI 分数 + エージェント利用料 + Apple Developer Program
4. **品質ゲート通過率** — App Review 一発通過率、クラッシュフリー率、TestFlight フィードバック対応時間

## 活かし方(このラボ → 量産)

1. E01〜E04 が通った時点で、このリポジトリの構造をテンプレートリポジトリ化する(E06)
2. 新アプリ = テンプレート instantiate → 企画・仕様(人間) → 機能を `agent:task` Issue に分解(人間+エージェント) → ループが消化
3. このラボ自体は「ループの実験場」として残し、新パターン(新しい CI 構成、新ツール)はまずここで試してからテンプレートに反映する
4. 失敗・介入の記録(metrics)はアプリ横断で集約し、テンプレートの改善に還元する
