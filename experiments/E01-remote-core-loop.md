# E01 — リモートコアループ

- **状態**: **完了(成功)** — 判定は末尾
- **対応する問い**: Q1(自律性)、Q3(コスト)の一部
- **フェーズ**: P0

## 仮説

コアロジック(SwiftPM パッケージ)の機能開発は、**リモート Linux 環境の Claude Code のみ**で、人間タッチ 2 回/PR(レビュー+マージ)以下で安定して回る。Mac は一切不要。

## 方法

1. `agent:task` Issue を 3 本起票する。例:
   - AppCore: `SemanticVersion` にプレリリース識別子(`1.2.3-beta.1`)対応を追加
   - AppCore: 「アプリ内お知らせの表示可否判定」(バージョン範囲+日付範囲)モジュールを追加
   - AppCore: 設定値のバリデーション付きストア(UserDefaults 抽象)を追加
2. 各 Issue を Claude Code(web)のセッションに渡し、実装 → PR → CI → レビュー対応 → マージまで流す
3. 人間は PR レビューとマージのみ行う(それ以外の介入はカウントして記録)

## 計測(loop-log.csv に記録)

- `human_touches`: レビュー・マージ以外も含む人間の介入回数
- `human_minutes`: 人間が使った合計時間
- `ci_runs` / `ci_failures`: CI 実行数と失敗数(初回 green か)
- Issue 起票からマージまでの経過時間(notes に記録)

## 成功基準

- 3 PR すべてマージ到達
- 平均 human_touches ≤ 2
- CI 初回 green ≥ 2/3
- 人間の合計時間 ≤ 15 分/PR

## 失敗時の見立て(事前に書いておく)

- 完了条件の書き方が曖昧 → Issue テンプレートの「完了条件」欄を改善(反映先: テンプレート)
- CI 環境差(ローカル Swift なし)での手戻り → CLAUDE.md の検証手順を改善
- レビューで大きな手戻り → タスク粒度を小さくする指針を CLAUDE.md に追加

## 観察メモ(実施中に追記)

- (2026-07-11) セッション初日: リポジトリ初期化自体をリモート Linux で実施。Swift 不在のため AppCore の検証は CI に委譲する構成を採用 — これ自体が E01 の前提(検証をリモートに寄せる)の実地確認になっている。
- (2026-07-11) ブロッカー発見: **空リポジトリ(コミット 0)にはエージェントの全書き込み経路(git push / GitHub App API)が 403 で拒否される**。GitHub App 統合は空リポジトリを初期化できない既知の制約。教訓: ループの前提条件に「リポジトリは人間が初期化済み(main に最初のコミットが存在)」を追加する。テンプレート化(E06)時はリポジトリ作成手順に「Add a README で初期化」を含めること。人間の介入 1 回としてカウント。
- (2026-07-11) ブロッカー2: リポジトリ初期化後も 403 が継続。原因は **Claude GitHub App の Repository access に新規リポジトリが未登録**だったこと(public リポジトリのため読み取りは通り、発見が遅れた)。教訓: 新規リポジトリ立ち上げチェックリストは「①Add a README で初期化 → ②GitHub App の Repository access に追加」の 2 点セット(E06 のテンプレートに反映予定)。量産期は App 設定を All repositories にする選択肢も検討。
- (2026-07-11) セットアップ PR #1 マージ。CI は core-ci / docs-ci とも初回 green(AppCore は Swift の無い環境で実装し、一度もローカル実行せずに CI 検証のみで green — L1/L2 の「検証をリモートに寄せる」設計の初回実証)。人間タッチ 4 回(リポジトリ初期化、App 権限付与、レビュー、マージ)のうち 2 回は環境ブートストラップ起因で、2 本目以降のタスクでは発生しない見込み。
- (2026-07-11) **L2 が初仕事**: PR #2 でエージェントが Python csv モジュールで CSV を書き換えた際、既定の行末(CRLF)が混入 → 目視では不可視のため自己検証をすり抜け → docs-ci のヘッダ完全一致チェックが検出。人手ゼロで検出→修正(sed で CR 除去+CI と同一チェックをローカル実行してから push)。教訓: 「見た目で確認」は検証ではない。機械的完全一致チェックは安い割に有効。
- (2026-07-11) **E01 タスク 1 本目着手**(Issue #3 → PR #4、SemVer プレリリース対応): リモート Linux(Swift 不在)で実装。コミット前に、パース規則と優先順位アルゴリズムを Python へ忠実移植し、Issue の完了条件チェーン+SemVer 2.0.0 §11.4 の公式チェーン+不正形式 11 種の計 70 チェックを機械検証してから、コンパイルと swift test を core-ci に委譲(「検証をリモートに寄せる」設計の 2 度目の実地確認。CI 修正 3 回上限を守るための事前検証としても機能)。運用上の発見: PR テンプレートは loop-log への「PR 内追記」を要求する一方、outcome 列の語彙(merged/abandoned/escalated)はマージ後にしか確定しない — PR #1 の行も実際には後続 PR #2 で確定されていた。今回は outcome=open で追記しマージ時の確定を残した。**記録タイミングの仕様ギャップ**として L4 の検討材料(反映先候補: metrics/README の列定義 or テンプレートの文言)。
- (2026-07-12) **E01 タスク 2 本目着手**(Issue #5 → PR #6、お知らせ表示可否判定): リモート Linux(Swift 不在)で実装。PR #4 のパターンを踏襲し、SemVer 比較+shouldDisplay 述語を Python へ移植、テスト全アサーション+日付×バージョンの全 35 組み合わせ truth table の計 57 チェックを機械検証してから core-ci に委譲(同設計の 3 度目の実地確認 — 手順が再現可能なパターンとして定着しつつある)。観察: Issue の完了条件は境界値テスト(開始/終了・min/max ちょうど)を明示する一方、境界を**含むか否か**自体は未指定だった。inclusive(両端含む)を自然な既定として採用し、PR の「人間に見てほしい点」でレビューに委ねた — 「仕様解釈が割れたら停止」には該当しないと判断(解釈の衝突ではなく、既定+HOTL ゲートで吸収できる未指定事項)。Issue テンプレートの「完了条件」欄が境界の向きまで書かせる形になっていれば判断は不要だった — テンプレート改善の L4 材料(E01 失敗時見立て 1 と同根)。
- (2026-07-12) **E01 タスク 3 本目着手**(Issue #7 → PR #8、バリデーション付き設定ストア): 計画した 3 タスクの最終。PR #4/#6 のパターンを踏襲し、ストアのセマンティクス(型付きキー・ルール・拒否理由・既定値フォールバック)を Python へ移植、テスト 22 メソッドの全アサーション+文字数 0〜30/時刻 −5〜30 の全域スイープの計 133 チェックを機械検証してから core-ci に委譲(「検証をリモートに寄せる」設計の 4 度目の実地確認)。観察 1: Issue はルールの**例**(ニックネーム文字数、時刻範囲)を挙げるが、具体的境界値・「文字数」の単位(書記素クラスタか Unicode スカラか)・バリデーションの置き場所(キー側かストア側か)は未指定 — PR #6 と同じく「自然な既定+『人間に見てほしい点』でゲートに委ねる」で吸収し、停止条件(仕様解釈の衝突)には該当しないと判断。この吸収パターンは 2 タスク連続で機能しており、E01 の運用上の標準になりつつある。観察 2: Python 移植による事前検証に初めて**忠実性の限界**が出た — Swift の Character(書記素クラスタ)数えは Python の len() と乖離するため、テスト入力に必要な範囲(国旗=regional indicator ペア)だけ移植側に再実装して埋めた。「Swift 固有のセマンティクスに仕様が依存するタスク」では移植コストが上がる、という手法の適用範囲メモとして L4 材料。

## 判定(2026-07-12、L4 1周目)

| 成功基準 | 結果 | 判定 |
|---|---|---|
| 3 PR すべてマージ到達 | 3/3(PR #4, #6, #8) | ✅ |
| 平均 human_touches ≤ 2 | 2.0(全 PR ともレビュー+マージのみ、修正指示・手戻りゼロ) | ✅ |
| CI 初回 green ≥ 2/3 | 3/3 | ✅ |
| 人間の合計時間 ≤ 15 分/PR | 未計測(記録の仕組み漏れ → 学び 5) | ⚠️ |

**判定: 成功。** 仮説「コアロジック開発はリモート Linux のみ・人間タッチ ≤2 回/PR で回る」は 3 タスク連続で支持された。Mac・ローカル環境・シミュレータは一度も使用していない。事前に書いた失敗時見立てのうち 1(完了条件の曖昧さ)は「未指定事項」という弱い形で 2 回顕在化したが、吸収パターン(既定採用+レビュー誘導)で手戻りゼロに抑えられた。2(CI 環境差の手戻り)と 3(レビュー手戻り)は発生しなかった。

### 学びと反映先(この判定と同じ PR で反映)

1. **二段階記録ルール**(PR #4/#6 が指摘した記録タイミングの仕様ギャップ)→ metrics/README・PR テンプレート・CLAUDE.md 作業ルール 4 に明文化
2. **Python 移植による事前検証パターン**(4 回再現・全 PR CI 初回 green の主因)→ CLAUDE.md 作業ルール 2 に昇格
3. **同パターンの適用限界**(書記素クラスタ等 Swift 固有セマンティクス)→ 同上に注意書きとして併記
4. **未指定事項の吸収パターン**(2 回機能)→ CLAUDE.md 停止・エスカレーションに「解釈が割れた」との区別を明文化
5. **human_minutes の記録漏れ** → metrics/README に「週次 L4 で人間が概算記入(または空欄可)」を明記
6. **Issue テンプレートの改善**(境界・単位を書かせる)→ agent-task.yml の完了条件欄を強化
