# 承認ポリシー — 変更クラスと HOTL ゲート

> 「どの変更に、どれだけ人間の注意を使うか」の定義。このファイル自体の変更は C2。
> 原則: **全部を丁寧に見る運用は必ず形骸化する。見ないものを先に決め、浮いた注意を高リスク変更に集中する。**

## 変更クラス

| クラス | 対象 | ゲート | 人間の見方 |
|---|---|---|---|
| **C0 自動** | `docs/`, `experiments/`, `metrics/` の追記、typo 修正 | CI green | **見ない**(週次 L4 でまとめて流し読み)。Phase 0 ではマージ操作のみ人間 |
| **C1 軽レビュー** | `packages/` のコード・テスト | CI green + 人間レビュー | PR の「エビデンス」と「人間に見てほしい点」を確認し、該当差分だけ読む。目安 5 分 |
| **C2 重レビュー** | `.github/`(CI・テンプレート)、`CLAUDE.md`、`loop/`、依存追加、アーキテクチャ変更、UI の大きな変更 | CI green + 人間精読 | 差分全体を読む。急がない。判断理由を PR コメントに 1 行残す(L4 の材料) |
| **C3 人間専任** | 署名・証明書・プロビジョニング、Capability、App Privacy・輸出規制、外部 TestFlight / App Store 提出、公開、課金、法的合意 | エージェントは**ドラフトのみ** | 実行は常に人間。ストア提出・公開は起案から**一晩置く**(クールダウン) |

## 運用ルール

1. PR は必ずテンプレートで変更クラスを自己申告する。クラス跨ぎ(C0 と書いて workflows を触る等)は差し戻し
2. 1 PR に複数クラスが混ざる場合、最も高いクラスとして扱う。**C3 に触れる差分はエージェント PR に含めない**(ドラフトは docs/ に置く)
3. エビデンス欄が空の PR はレビューせず差し戻す
4. C2 の差し戻し・修正は metrics に記録し、L4 で「ゲートが機能したか」を評価する
5. 将来 C0 の auto-merge を導入する場合も、E03 で差し戻し率の実績を見てから(いきなり自動化しない)

## このポリシーの検証(E03)

- C0 ノールック運用で事故(意図しない変更の混入)がゼロか
- C1 の 5 分レビューで不具合を捕捉できているか(すり抜けたバグの事後分析)
- C2 の精読が機能しているか(差し戻し率が 0% なら形骸化を疑い、ゲートを見直す)
